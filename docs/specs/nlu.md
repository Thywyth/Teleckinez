# Специфікація: розбір команд (NLU)

Вхід — текст (з STT або клавіатури), вихід — `Intent`:

```python
@dataclass
class Intent:
    kind: Literal["command", "query"]
    action: str | None            # turn_on, turn_off, open, close, set, step, start, stop, lock, unlock …
    device_type: str | None       # light, curtains, …
    device_name: str | None       # конкретна назва, якщо вказано («люстра»)
    room: str | None
    group: str | None             # all_lights …
    params: dict                  # {"brightness": 40} / {"position": 50} / {"target_temp": 22}
    lang: str
    confidence: float
    raw_text: str
    parser: str                   # "rule" | "llm"
```

## 1. Правила + fuzzy (`RuleParser`, за замовчуванням)

1. **Нормалізація:** нижній регістр, прибрати пунктуацію, `ё/ї` варіанти,
   апострофи (’ ' ʼ), числівники → цифри (`двадцять два` → 22, `half/наполовину`
   → 50), «відсотків/%», «градусів/°».
2. **Мова:** за алфавітом (кирилиця/латиниця); змішані фрази дозволені.
3. **Дія:** словник `lexicon.py` — дієслова і їхні форми:
   `turn_on`: увімкни, ввімкни, включи, запали, увімкнути, turn on, switch on …;
   `open`: відкрий, відчини, підніми, open, raise …
   Фрази без дієслова («штори вітальня») → дія за замовчуванням для типу
   (для штор — toggle, для світла — toggle), це вимога автора.
4. **Кімната і пристрій:** пошук синонімів з devices.yaml як n-грам у тексті;
   стійкість до відмінків і помилок STT — `rapidfuzz` (token_set_ratio,
   поріг ~85) + порівняння за основою слова (перші N літер). Опційно —
   лематизація `pymorphy3` з українським словником.
5. **Параметри:** регулярні вирази для чисел з одиницями, слова «гучніше/
   тепліше/яскравіше» → `step` з кроком за типом.
6. **Confidence** = комбінація оцінок fuzzy-збігів; нижче порогу → `IntentFailed`.

**Уточнення етапу 1 (реалізація):**
- Збіг фрази шукається «найдовшим першим» (до 4 слів) у три кроки: точний
  (оцінка 1,0) → за основою слова для відмінків (0,9: «кухні» ~ «кухня») →
  `rapidfuzz.fuzz.ratio` ≥ порогу (оцінка = ratio/100). Confidence — середнє
  оцінок ключових слотів.
- Парсер не завжди знає тип цільового пристрою, тому в `Intent.params` кладе
  **загальні** значення: `percent` (40 %), `degrees` (22°), `number`, `step`
  (`{"attribute", "direction", "amount"}`), або явний атрибут, якщо його
  названо («яскравість 40»). `TargetResolver` перетворює їх на атрибут
  конкретного типу: `percent` → `brightness` для світла, `position` для штор.
- «Відкрий на 30 %» → положення 30; «закрий наполовину» / «на 30 %» → 50 / 70.
- Якщо названий пристрій не має потрібного атрибута, resolver шукає в тій
  самій кімнаті пристрій тієї ж родини («зроби світло синім» → RGB-торшер).

Приклади, що мають розбиратися однаково:
`штори вітальня` · `відкрий штори у вітальні` · `living room curtains` ·
`open the curtains in the living room`.

## 2. Обмежена граматика для Vosk

З того самого словника генерується список фраз/слів для Vosk-граматики
(`nlu/grammar.py`) — розпізнавач тоді «чує» лише відомі слова, що різко
підвищує точність на командах. Це спільне джерело правди для STT і NLU.

## 3. Локальна LLM (`LlmParser`, P2, опційно)

- Ollama + невелика модель (напр. `qwen2.5:3b` / `llama3.2:3b`; на RTX 3060
  6 GB поміщається 7B у 4-bit) — точну модель обрати на етапі експериментів.
- Промпт: перелік кімнат/пристроїв/дій з devices.yaml + фраза; відповідь —
  JSON за схемою `Intent` (structured output у Ollama). Валідація pydantic;
  невалідна відповідь → fallback на `RuleParser`.
- Режими: `rule`, `llm`, `hybrid` (спершу правила; якщо confidence низький —
  LLM). Порівняння точності і затримки — у metrics.md; це дає матеріал для
  аналітичного розділу «класичний NLU vs LLM».

**Реалізація етапу 4** (`nlu/llm_parser.py`):
- Ollama 0.40.6 (встановлено через `winget install Ollama.Ollama`), модель
  `qwen2.5:3b` (2,2 ГБ), `temperature 0`, structured output: JSON-схема
  відповіді будується з devices.yaml — кімнати, назви пристроїв, групи, дії,
  кольори, режими є `enum`, тому модель не може назвати неіснуючий пристрій.
  У промпті — перелік кімнат/назв/груп і 8 прикладів (few-shot).
- Відповідь моделі (pydantic) перетворюється на той самий `Intent`, що й у
  RuleParser (із загальними `percent` / `degrees` / `step`), тож resolver і
  диспетчер не залежать від того, хто розібрав фразу.
- Fallback на RuleParser: Ollama недоступна, таймаут (`llm_timeout_s`),
  невалідний JSON. Відповідь `kind: unknown` вважається «не зрозумів».
- `hybrid`: LLM викликається, якщо правила не впоралися або
  `min(confidence, coverage) < hybrid_threshold` (0,8). **Coverage** — частка
  значущих слів, які правила розпізнали: у «приглуши трохи торшер» правила
  бачать лише «торшер» (1/3) і без LLM перемкнули б торшер замість
  приглушити.
- На старті асистента в режимах llm/hybrid модель «прогрівається» у фоні:
  холодний старт першого запиту без цього перевищував 60 с.
- Перші ручні заміри (20.10.2026, не для записки — у звіт ідуть лише
  результати E2): 2,6–4,9 с на запит, модель працювала на 95 % CPU, бо GPU
  був зайнятий іншою програмою; 8 з 10 пробних фраз розібрано правильно,
  помилки: «на кухні темнувато» → вимкнути (а не увімкнути), «зроби торшер
  фіолетовим» → не той пристрій.
