# Архітектурні рішення (ADR)

Формат: контекст → рішення → альтернативи → наслідки. Цей файл — основа для
розділу 2 записки («обґрунтування вибору»). Нові рішення додаємо в кінець.

---

### ADR-001. Подієво-орієнтований модульний моноліт
- **Контекст:** один розробник, місяць часу, демонстрація на одному ноутбуці,
  але потрібна архітектура, яку можна обґрунтувати й розвивати.
- **Рішення:** один процес асистента з модулями, що спілкуються через
  внутрішню шину подій; пристрої/симулятор — окремі процеси через MQTT.
- **Альтернативи:** мікросервіси (надмірна операційна складність:
  розгортання, мережеві збої між власними ж сервісами); класичний шаровий
  моноліт з прямими викликами (сильна зв'язаність, важко додати веб-панель
  і метрики як «спостерігачів»).
- **Наслідки:** модулі легко замінювати й тестувати ізольовано; межі модулів
  збігаються з межами потенційних сервісів, тому перехід на мікросервіси
  можливий без зміни контрактів.

### ADR-002. MQTT як протокол взаємодії з пристроями
- **Альтернативи:** HTTP/REST (pull-модель, немає push-станів і LWT), CoAP
  (UDP, менше інструментів), WebSocket (немає семантики QoS/retain),
  Zigbee/Z-Wave/Matter (фізичний/мережевий рівень, потребують залізо —
  підключаються *через* MQTT-міст).
- **Чому MQTT:** publish/subscribe, QoS 1, retained-повідомлення для
  останнього стану, **Last Will** для миттєвого виявлення відключення, легкий
  для мікроконтролерів, підтримка в Tasmota/ESPHome/Zigbee2MQTT/Home Assistant.

### ADR-003. Повністю локальна обробка мовлення
- **Причини:** приватність (аудіо не залишає будинок), робота без інтернету,
  передбачувана затримка, вимога автора.
- **Ціна:** точність і вимоги до заліза; компенсується обмеженою граматикою
  і вибором рушія під залізо.

### ADR-004. Два STT-рушії за спільним інтерфейсом: Vosk і faster-whisper
- Vosk (Kaldi, гібридна HMM/DNN модель): малий, швидкий, працює на Raspberry
  Pi, підтримує обмежену граматику, є українська модель.
- Whisper (трансформер encoder–decoder, faster-whisper/CTranslate2): краща
  якість на вільній мові, багатомовність, але повільніший і вимагає GPU для
  комфортної роботи.
- Рішення про рушій за замовчуванням ухвалюємо **за результатами E1**.

### ADR-005. Гібридний NLU: правила + fuzzy як основа, LLM — опція
- Набір дій у розумному будинку обмежений і відомий з конфігурації → правила
  дають детермінованість, мілісекундну затримку, пояснюваність.
- LLM краще розуміє вільні формулювання, але повільніша, може
  «галюцинувати» пристрої; тому лише structured output + валідація + fallback.

### ADR-006. Контроль виконання через цифровий двійник і автомат станів команди
- Підтвердження прийому (ack) ≠ виконання. Успіх фіксується лише коли
  фактичний стан пристрою збігся з бажаним (підхід на кшталт «device shadow»
  в AWS IoT / Azure Device Twin).
- Явний скінченний автомат дає повний перелік результатів, які можна
  перевірити тестами й описати діаграмою станів.

### ADR-007. Симулятор як окремий процес з ін'єкцією збоїв
- Чесно моделює мережеву взаємодію (окреме MQTT-з'єднання і LWT на пристрій),
  дозволяє відтворювано викликати збої для експериментів, що з реальним
  залізом складно.

### ADR-008. FastAPI + WebSocket + vanilla JS для веб-панелі
- Асинхронність збігається з рештою системи (asyncio), WebSocket для
  потоку подій, автоматична OpenAPI-документація. Без фронтенд-фреймворку і
  збірки — менше залежностей, працює офлайн.

### ADR-009. YAML для конфігурації, SQLite для журналів
- Конфігурацію пристроїв і синонімів редагує людина → YAML.
- Журнали/історія/метрики → SQLite: вбудована, без сервера, достатня
  продуктивність, SQL-запити для бенчмарків. TSDB (InfluxDB) — надмірна для
  масштабу прототипу, згадати як перспективу.

### ADR-010. Брокер Mosquitto у Docker
- Еталонна реалізація MQTT від Eclipse, мінімальна конфігурація. Fallback —
  вбудований брокер на Python (перевірити на етапі 0).
- **Перевірено 20.10.2026:** образ `eclipse-mosquitto:2`, конфіг
  `config/mosquitto/mosquitto.conf` (анонімний доступ — лише для локального
  демо, persistence для retained-станів). Fallback — `amqtt` 0.12.1 на
  Python 3.13, проходить ті самі інтеграційні тести (QoS 1, retain, LWT).
  Mosquitto лишається основним: він швидший і стабільніший під ~30
  з'єднаннями симулятора; amqtt — запасний варіант для машини без Docker.

### ADR-011. Python 3.13
- Встановлений у системі. Якщо vosk / piper / openwakeword не мають колесиків
  під 3.13 — переходимо на 3.12 і записуємо це сюди.
- **Перевірено 20.10.2026** (Windows 11, Python 3.13.2, `scripts/check_deps.py`):
  усі ключові залежності ставляться з готових колесиків і імпортуються —
  aiomqtt 2.5.1, numpy 2.5.4, sounddevice 0.5.6, webrtcvad-wheels 2.0.14.post1,
  vosk 0.3.45, faster-whisper 1.2.1 (ctranslate2 4.8.3), piper-tts 1.8.0,
  onnxruntime 1.31.0, openwakeword 0.6.0, pyttsx3 2.99, pynput 1.8.2,
  ollama 0.6.3. **Рішення: залишаємось на Python 3.13.** У `pyproject.toml`
  стоїть `requires-python >=3.12`, щоб проєкт також працював на 3.12 (напр.
  на Raspberry Pi OS).
- **CUDA для faster-whisper.** ctranslate2 бачить RTX 3060 (float16/int8),
  але для інференсу на GPU потрібні cuBLAS 12 і cuDNN 9, яких у системі
  немає. Замість встановлення CUDA Toolkit беремо їх з pip-колесиків
  `nvidia-cublas-cu12` і `nvidia-cudnn-cu12` (extra `cuda`, ≈1 ГБ) і
  додаємо їхні теки `bin` у шлях пошуку DLL
  (`teleckinez.voice.cuda.register_cuda_dlls()`). Без extra `cuda`
  faster-whisper працює на CPU (int8).
- openWakeWord на Windows — лише через onnxruntime (tflite-runtime для
  Windows немає), що й передбачено у voice.md.
- **Шляхи з кирилицею.** Нативні бібліотеки Vosk (Kaldi) і espeak-ng (у
  Piper) не відкривають файли за не-ASCII шляхом на Windows. Замість
  перенесення проєкту з теки «Курсоваробота» передаємо їм ASCII-шлях
  (`teleckinez.voice.paths.ascii_safe_path`: відносний або 8.3). Моделі
  перевіряються командою `python scripts/download_models.py --verify`
  (20.10.2026: Vosk uk/en, faster-whisper small на CUDA float16, Piper uk/en,
  openWakeWord — усі працюють).
